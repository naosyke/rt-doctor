# rt-doctor 使い方ガイド

このガイドは、「Linux で動かしているプログラムが、ときどき期限に間に合わない」ときに、rt-doctor で原因を見つけて直し、
直ったことを確かめるまでの手順です。

例として、**1 ms ごとに動くはずのロボットの制御プログラム `motor_ctrl` が、ときどき遅れて動きがカクつく**場面で説明します。

## 1. 準備

必要なものは次のとおりです。

* **実機の Linux**（ロボットの PC、Jetson、Raspberry Pi、産業用 PC など）。x86-64 と arm64 に対応しています。
* **sudo（管理者権限）**。カーネルの記録（ftrace）を読むのと、root でしか見えない設定を見るのに必要です。

画面のない機械でも、SSH でつないだ黒い画面（ターミナル）でそのまま使えます。

インストールは1行です。

```bash
curl -fsSL https://github.com/naosyke/rt-doctor/releases/latest/download/install.sh | sh
```

マシンに合う版（x86-64 か arm64 か）を自動で選び、改ざんがないか確認してから `/usr/local/bin/rtdoctor` に入れます。

## 2. いちばん簡単な方法: 対話モード

**調べたいプログラムを、いつもどおり動かしたまま**、次のコマンドを打ちます。

```bash
sudo rtdoctor
```

あとは質問に答えるだけです。

### [1/3] システムの診断

何も入力しなくても、自動で設定を診断して、影響の大きい問題から順に表示します。

```text
[1/3] このシステムを診断しています…
  一番の要因: カーネルのプリエンプション方式 - プリエンプション: なし、または voluntary
  次に:       隔離CPU - なし
  次に:       CPU周波数の制御 - ondemand（CPU 0-3）
  理由と直し方は、最後に作るレポートに書いてあります。
```

### [2/3] プログラムを選んで、遅れの原因を調べる

rt-doctor が、**今このマシンで動いているプログラム**を1秒間観察して、調べる候補を挙げます。

```text
[2/3] 遅れを調べたいプログラムを選びます。動いているプログラムを1秒間観察しています…
  リアルタイム優先度のあるもの、次に起きる回数が多いものの順です:
   1) ros2_node        pid 1826    リアルタイム FIFO 80、1秒に 1000 回起きる（約 1.0 ms ごと）、スレッド motor_ctrl
   2) planner          pid 1902    1秒に 100 回起きる（約 10.0 ms ごと）
   3) ros2_logger      pid 2210    1秒に 20 回起きる（約 50.0 ms ごと）
  番号・pid・名前のどれかを入力（Enter で飛ばす）: 1
```

候補の選び方は、次のとおりです。

* **リアルタイム優先度で動いているプログラム**を先頭に出します。誰かが「これは時間に厳しい」と設定したものなので、調べる価値が一番高いからです。
* 次に、**1秒間に何回「起きて、寝た」か**が多い順に出します。制御ループのような周期的なプログラムは「起きて仕事をして寝る」を規則正しく繰り返すので、回数が多くなります。回数から周期の目安（「約 1.0 ms ごと」）も計算します。
* カーネル内部のスレッドと、rt-doctor 自身は除きます。

候補に出ないプログラムでも、**pid か名前を直接入力**すれば調べられます。rt-doctor が何かを起動するわけではないので、
調べたいプログラムは、自分であらかじめ動かしておく必要があります。

続けて、期限と時間を聞かれます。

```text
  期限は何 ms ですか？ふつうは周期と同じです [1.0]:
  何秒間見張りますか？ [10]: 30
```

* **期限**: その処理が終わっていてほしい時間です。ふつうは周期と同じにします。`[ ]` の中は観察から推定した値で、Enter だけ押すとそれを使います。
* **時間**: 長いほど、まれに起きる遅れを捕まえやすくなります。数十秒〜数分がおすすめです。Ctrl+C で途中で終われます。

見張っている間は、**いつもどおりの負荷をかけてください**（ロボットを動かす、ログを出す、通信するなど）。
遅れは、ほかの処理が動いているときに起きるからです。

```text
  スレッド motor_ctrl: 30000 回実行、期限切れ 41 回、最悪 3.20 ms
  一番の原因: タスク ros2_logger (pid 2210)、38.20 ms
  対策: タスクが動ける状態なのに、同じ CPU で別のタスクが動いていました。…
```

### [3/3] レポート

すべての結果を、HTML のレポートにまとめます。

```text
[3/3] レポートを作っています…
  /home/robot/rtdoctor-report-20261012-101500.html
  ブラウザで開いてください。別の PC で見るには: scp <このマシン>:/home/robot/rtdoctor-report-20261012-101500.html .
```

画面のない機械なら、`scp` で手元の PC にコピーしてからブラウザで開きます。

## 3. コマンドで1つずつ進める方法

対話モードと同じことを、コマンドで1つずつ行うこともできます。手順書やスクリプトに書くときは、こちらが便利です。

### 手順1: システムを診断する

```bash
sudo rtdoctor check
```

先頭の **Summary** に、一番の問題と次に直すものが出ます。各項目の **Why:** に理由、**Fix:** に直し方が書いてあります。
問題のない項目の説明も見たいときは `--verbose` を付けます。

### 手順2: 調べたいプログラムの pid を調べる

```bash
pgrep motor_ctrl
ps -eLo pid,tid,cls,rtprio,comm | grep motor_ctrl
```

1行目で pid がわかります。2行目では、スレッドごとの番号（tid）、スケジューリングの方式（`FF` = FIFO）、リアルタイム優先度、
スレッド名がわかります。

### 手順3: 遅れの原因を調べる

```bash
sudo rtdoctor trace --pid 1826 --duration 30 --deadline-ms 1
```

| オプション | 意味 |
|---|---|
| `--pid 1826` | このプロセスのすべてのスレッドを調べる |
| `--comm motor_ctrl` | `--pid` の代わりに、スレッドの名前で指定する |
| `--duration 30` | 30秒間見張る（Ctrl+C で途中終了） |
| `--deadline-ms 1` | 期限 1 ms を超えた回を「期限切れ」として数える |
| `--threads 5` | 表示するスレッドの数（初期値 3） |
| `--json` | ほかのツールで処理する形式で出す |

### 手順4: 直す

結果のアドバイスに従って直します（[5. よくある原因と直し方](#5-よくある原因と直し方)）。

### 手順5: 直ったか確かめる

手順3と**同じコマンド、同じ負荷**で測り直します。期限切れが減っていれば効果があります。

### 手順6: レポートにまとめる

```bash
sudo rtdoctor report --lang ja -o report.html --pid 1826 --duration 30 --deadline-ms 1
```

`--pid` などを付けなければ、システムの診断だけのレポートになります。

## 4. 結果の読み方

### システムの診断の判定

| 判定 | 意味 | 健康診断なら |
|---|---|---|
| PASS | リアルタイム向けの良い設定。何もしなくてよい | 異常なし |
| INFO | それだけでは問題ではない参考情報 | 参考所見 |
| WARN | 遅れの原因になりうる。直した方がよい | 要注意 |
| FAIL | このままではリアルタイム処理がまともに動かない | 要治療 |

WARN と FAIL には**影響の大きさ**（致命的・大・中・小）が付きます。**影響の大きいものから直す**のが近道です。
小さいものをいくら直しても、大きな原因が残っていると効果は見えません。

### 遅れの原因調査の数字

| 表示 | 意味 |
|---|---|
| 実行回数（activations） | 「起きてから、仕事をして、また寝る」までを1回と数えた回数 |
| 期限切れ（over the deadline） | 1回にかかった時間が期限を超えた回数 |
| 応答時間の中央値 / 99パーセンタイル / 最悪 | 1回にかかった時間。ふつうの回、100回に1回の悪い回、一番悪い回 |
| CPU の空き待ち（waiting） | 動ける状態なのに、CPU が空かずに待たされていた時間 |
| 横取り（preemptions） | 実行中に、ほかのものに CPU を取られた回数 |

### 「誰が遅らせたか」の名前

| 名前 | 意味 |
|---|---|
| タスク 名前 (pid N) | **ほかのプログラム**が、その CPU を使っていた |
| 割り込み irq N 名前 | ネットワーク、ディスク、タイマーなどの**割り込み処理**が動いていた |
| softirq 名前 | 割り込みの**後処理**が動いていた |
| idle（CPU の休止中） | CPU は空いていたのに、**休止状態からの復帰**に時間がかかった（または仮想マシンが止まっていた） |

### レポートの「時間がかかった回ワースト」の棒

1本の棒が1回分です。左から右へ時間が流れます。

* **灰色**: 自分の処理の時間
* **色付き**: 待たされた時間（色が原因の種類。オレンジ = ほかのタスク、紫 = 割り込み、青 = softirq、緑 = 休止からの復帰）
* **赤い点線**: 期限

灰色が長ければ**プログラム自体が重い**ので、処理を軽くする必要があります。色付きが長ければ**ほかのものに邪魔されている**ので、
設定で直せます。

## 5. よくある原因と直し方

| 原因 | 直し方の例 |
|---|---|
| ほかのタスクに邪魔された | 遅れたプログラムにリアルタイム優先度を付ける: `sudo chrt -f -p 80 PID`<br>または邪魔したタスクを別の CPU に移す: `sudo taskset -cp 3 PID` |
| 割り込みに邪魔された | 割り込みを別の CPU に回す: `echo 0-1 \| sudo tee /proc/irq/N/smp_affinity_list` |
| 休止からの復帰が遅い | 深い休止状態を止める（システムの診断の「CPUの深い休止状態」の対策を参照） |
| カーネルがリアルタイム用でない | PREEMPT_RT カーネルを使う（Ubuntu: `linux-realtime`、Debian: `linux-image-rt-*`） |
| CPU を共有している | 起動オプションで CPU を隔離し（`isolcpus=2-3 nohz_full=2-3 rcu_nocbs=2-3`）、プログラムをそこに固定する |
| リアルタイム優先度を使う権限がない | `/etc/security/limits.conf` に `@realtime - rtprio 98` を追加する、またはプログラムに `CAP_SYS_NICE` を与える |

`chrt` や `taskset` で変えた設定は、プログラムを再起動すると元に戻ります。効果を確かめたら、起動スクリプトや
systemd のユニットファイル（`CPUSchedulingPolicy=fifo`、`CPUSchedulingPriority=80`、`CPUAffinity=3`）に書いて、
毎回同じ設定で起動するようにします。

## 6. よくあるつまずき

**「Tracing was not possible」「調査できませんでした」と出る**
: root で実行していないか、カーネルのトレース機能（tracefs）が使えません。`sudo` を付けてください。
  コンテナの中で実行するときは、`docker run --privileged` が必要です。

**「no activations」「一度も「起きて寝る」をしませんでした」と出る**
: そのプログラムが寝ずに計算し続けているか（周期的に休まない）、指定した pid・名前が違います。
  `ps -eLo pid,tid,comm` でスレッドの名前を確かめてください。

**コンテナ（Docker）の中のプログラムを調べたい**
: コンテナの中では、プロセスの番号がカーネルの記録と違うため、rt-doctor は自動でスレッドの**名前**で照合します。
  同じ名前のスレッドがほかのプロセスにもあると、それも含まれます。正確に調べたいときは、ホスト側で実行するか、
  `docker run --pid=host` でコンテナを起動してください。

**システムの診断で「仮想マシン」が一番の要因になる**
: 仮想マシン（Docker Desktop、WSL 2、クラウドの普通のインスタンスなど）は、外側のソフトがいつでも一時停止できるため、
  どう設定しても期限切れはゼロになりません。リアルタイム性能は実機で測ってください。

**レポートを別の PC で見たい**
: `scp ユーザー@マシン:/パス/report.html .` で手元にコピーして、ブラウザで開きます。レポートはネット接続なしで開けます。

**「kernel dropped N trace events」「記録を取りこぼしました」と出る**
: 記録が多すぎてカーネルのバッファがあふれました。`--duration` を短くしてください。

## 7. 自動テスト（CI）で使う

設定が知らないうちに変わって、リアルタイム性能が落ちるのを防げます。

```bash
rtdoctor check --fail-on warn
```

WARN 以上が1つでもあれば終了コード 1 になるので、CI のジョブを失敗させられます。結果を記録したいときは `--json` を付けます。

```bash
rtdoctor check --json > rtdoctor.json
```

`priorities` に、直すべき項目が影響の大きい順に入っています。
